# Effort–Result · Release 1 · server collection

Add **Indicators → Order Flow → Effort–Result** to a Binance BTCUSDT USD-M perpetual chart. The active list owns settings, visibility and removal. A compact status button in the reserved chart footer below the plot and footprint totals shows availability and opens retained events; event markers expose the same evidence on hover. “Show signed intensity pane” is optional. Candidate notifications, outcome notifications and sound default off and use the terminal’s existing master mute, audio permission, delivery and visibility policy.

This is an observation of unusually strong directional aggressive trading with limited price progress in a narrow, persistent zone. **Buy flow stalled — potential passive selling** and **Sell flow stalled — potential passive buying** describe observations, not identified participants, position opening/closing, icebergs, reversal probabilities or trading instructions. No orders are placed.

## Supported inputs and clocks

Release 1 enables **Binance BTCUSDT USD-M perpetual aggregate executions, BTC quantity, trade-price proxy, exchange execution clock, rolling 30 seconds**. The server observer reads normalized, unfiltered durable executions from the existing Binance recorder. It opens no additional exchange connection. Neither a client window, Footprint nor Trade Ticker needs to be open. `q` retains the incumbent total execution-volume semantics, including RPI-related volume. It is never replaced by `nq` or compared with ordinary displayed-book depletion to estimate hidden size. Aggregate records do not identify one trader or parent order.

The actual metadata tick size must match the supported USD-M 0.1 tick identity. A changed tick contract is unavailable until a compatible source is configured. Spot and Hyperliquid remain unavailable for this indicator in Release 1; no new integration or cross-venue substitution is made.

There are **no midpoint, receipt-clock or book-evidence modes** in this release. Existing book observation timestamps do not establish exchange-time synchronization. Prices are the same-market execution path, with the latest eligible execution price at each boundary and all intra-second extrema. Seconds use `[start,end)` exchange execution timestamps; boundary executions at exactly start determine that boundary price in stable source order. Receipt timestamps are retained by normalization separately from execution/event times. Signal availability uses actual server processing time after the database read, never a candle opening time or the start of a database request. Retained executions can restore calibration, but restoration issues no historical candidates, outcomes, pane scores or alerts.

The default event-time lateness allowance is 500 ms (advanced range 0–5000 ms). The watermark advances from observed exchange execution timestamps minus that allowance, not an assumed host/exchange clock alignment. No outcome close is finalized merely because the host clock advanced. An observation gap over 15 seconds, stale/failed transport, epoch change, known sequence gap, upstream discard or out-of-policy late observation quarantines affected windows and interrupts pending outcomes. This deliberately favours unavailable data over invented quiet activity. Late corrections invalidate affected calibration references and append quality provenance to affected original evidence; issued candidates are never silently recalculated. No pending three-close run crosses a gap.

## Calibration and calculation

The implementation follows [the preserved research specification](iqterminal-effort-result-spec.md), sections 3–6. There is one evaluation per finalized second, independent of candle interval, zoom, display units or chart visibility. Non-overlapping 30-second UTC-aligned reference windows are eligible only when their end is at/before analysis start. Effort uses trailing 24-hour side-specific references and the half-tie percentile rank; at least 500 valid observations are required (about 4h 10m of continuous collection). All-zero side-specific history is unavailable. The prior-two-hour median range requires 100 references. Unknown-side quality also gates calibration observations.

The frozen scale is `max(median reference range, 4 × tick basis points)`. Trade-price proxy omits the unavailable spread term; this limitation remains explicit. The zone half-width and buffer each round up `max(2 ticks, 0.10 × start price × S / 10000)` to native ticks. Zone selection uses the highest-volume contiguous interval of full width `2h`; tied volumes choose centre nearest the current eligible price, then lowest lower bound. It does not use footprint rows or chart zoom.

Defaults: dominant-side effort percentile ≥0.95; absolute delta/total ≥0.30; unknown volume ≤0.01; directional maximum excursion ≤0.25S; absolute endpoint return ≤0.25S; whole range ≤S; zone concentration ≥0.50; at least three of six five-second parts each ≥0.10 of zone dominant-side volume; actual zone execution duration ≥10 seconds; current price within buffered zone. Directional extrema reject a large round trip even when endpoint return is small. Cheap quality/warm-up/effort gates precede histogram scanning.

The pane uses `−side × 100 × E × (1 − min(1,M/S))`: positive is sell aggression stalled, negative is buy aggression stalled. A valid evaluated non-signal window is zero; unavailable, warming-up or invalid is null. Intensity describes the current evidence, not confidence or probability. Null intervals break the plotted path.

## Events, settings and notifications

Detection freezes source identity, settings/version, zone, buffer, scale, original evidence, analysis start/end and actual availability. Later overlapping market/side/zone detections update one episode. Additional volume counts only disjoint seconds after the prior evidence endpoint inside the **original** zone; original detection evidence remains separate. Historical rolling-window volume is never counted again.

States are detected, rejection observed, breakthrough observed, expired/unresolved, and interrupted/unknown. Three consecutive **subsequent finalized one-second closes whose intervals begin after detection availability** and whose execution receipts are after detection availability must lie strictly beyond the frozen buffered boundary. Buy stalls reject below and break above; sell stalls reject above and break below. Confirmation availability is the processing time of the third close, never the start of the analysis window. This conservative full-interval rule prevents using a close partly observed before a delayed signal became available.

The default outcome horizon is 120 seconds from detection availability. Expiry is unresolved, not a loss or win. Interrupted continuity is unknown. Completed segments stop at their actual completion/expiry/interruption; the original marker remains, with R/B/U/? outcome notation. There are no permanent forward rays or retrospective candle colours.

Same-zone rearming uses a deterministic 60-second cooldown after completion availability; a genuinely new non-overlapping zone can form independently. A rearmed same-zone analysis window must also begin after the preceding episode’s evidence endpoint, so shorter advanced cooldowns cannot reuse its executions. Failed breakthroughs and unresolved/interrupted observations are retained on equal terms with rejections. Existing records retain their original calculation configuration. Changing calculation settings registers a compatible keyed server pipeline. The default pipeline starts with the supervised service, and registered configurations continue collecting even when every client is closed. Client removal stops polling/rendering, not server observation. Up to eight persistent calculation configurations are supported; capacity is explicit rather than silently evicting an active calculation. Reattaching the old settings reads its retained records. Presentation or timeframe changes do not reset compatible calibration.

Calculation settings, presentation preferences and notification preferences have separate persisted fields. Advanced detection thresholds are collapsed. Settings validation bounds unknown-side tolerance to at most 1%, persistence to at least three parts and duration to at least W/3. Alert delivery is deduplicated by stable event ID/transition through durable server-side claims, including across browser reloads and concurrent clients; `alertedAt` is recorded only after the existing notification gate acknowledges accepted delivery, independently from candidate/outcome availability. Restored events are marked historical and do not emit old alerts. Master notification settings and the existing freshness/rate/visibility policy still apply. Muted or hidden-page notifications are not replayed later.

## Persistence, export and replay

Calibration and version-1 events now use server-owned SQLite (`state/effort-result/effort.sqlite`, WAL and FULL synchronization), separate from workspace JSON. Keys include venue, market, symbol, quantity unit, source granularity, tick size, price/clock mode, 30s horizon, rolling-24h scheme, detector version and calculation settings. The existing Binance ClickHouse execution recorder remains the raw source; this service creates no replacement collector or trade table.

On first start or registration, the observer restores up to six hours of genuine retained executions through the same detector engine in **calibration-only mode**. That is sufficient to meet the 500-window minimum when coverage is valid; it does not claim a full 24-hour sample immediately. Live collection then fills the trailing 24-hour baseline. A normal observer restart restores its saved calibration, replays enough genuine recent executions to reconstruct the rolling price path, and marks pre-restart pending outcomes interrupted/unknown. It never assumes the process observed the market while it was stopped. Existing browser IndexedDB records remain untouched; they are not uploaded or mixed into server calibration.

Opening the client therefore reads existing server readiness instead of starting a fresh four-hour calibration. The server must still have enough valid data: a recorder outage, missing retained inputs, new unsupported configuration or long server shutdown can require restoration or further warm-up. A closed browser alone no longer causes the two-hour range history to go stale.

Default event retention is 30 days (1–90 configurable), bounded to 2048 oldest-first events per calculation without favouring successful outcomes. References hold at most 2882 aligned windows. SQLite is bounded to 64 MiB, each snapshot to 6 MiB, and eight registered configurations; capacity/write failures are explicit and suppress readiness rather than claim durability. Configurations are shared server resources; retention changes apply to the selected calculation configuration. Snapshots and source progress are checkpointed together every 30 seconds and at event transitions; notification claims are separately durable before delivery. Shutdown saves explicit interruptions. Browser closure does not interrupt server events.

The client polls through `/market-data/v1/effort-result`, proxied by the existing loopback API gateway. It requires server mode and has no silent local-calculation or fixture fallback. Initial history reconciliation never sends historical alerts. Session-token-protected registration/notification endpoints follow the existing private loopback-origin policy; there is no internet-facing listener.

Use **status → Export retained evidence** for versioned calibration/events, frozen settings and provenance. The export explicitly says that exact execution inputs are **not** retained. The existing Level Watch journal remains separate. The observer’s versioned SQLite records and evidence export provide the indicator-specific persistence boundary without changing Level Watch encounters.

For deterministic replay of actually supplied normalized execution inputs:

```sh
node scripts/effort-result-replay.mjs input.json output.json
```

Input schema is `{ "schema":1, "source":<source identity>, "settings":{}, "calibration":<optional saved snapshot>, "inputs":[...] }`. Omit source for the supported Binance proxy identity. Each input is `{ "trade":<NormalizedExecution>, "receivedAt":<actual availability ms>, "epoch":"source epoch" }`, or a batch-finalization frame `{ "trades":[...], "receivedAt":..., "epoch":... }`. Keep actual availability order, batch boundaries and epoch identity. Frames may include `interruption` and `correctionTime` for known quality events. Empty frames carry interruptions without manufacturing executions. Calibration/event exports alone cannot replay exact microstructure. No quote or execution history is reconstructed from candles.

The CLI compiles and runs the same DOM-free `EffortEngine` used by the server observer; it does not duplicate detector formulas. Output records event/observation availability, points, retained evidence and bounds. Prefix replay exposes only outcomes confirmed by that prefix. Inputs are capped at 256 MiB / two million frames; larger research runs require chronological segments with explicit discontinuities. Saved exports are calibration/event snapshots, not full streaming checkpoints: they cannot seamlessly resume active outcomes or the rolling execution ring. This is a replay/export route, not a backtesting or execution platform.

## Resource ownership and measured checks

One always-running server calculation is shared per compatible source/horizon/settings, regardless of chart timeframe/presentation or client lifetime. The client feed worker shares one poller per configuration. Hidden indicators stop rendering; removal of the last client consumer releases polling only. There is no per-chart trade websocket, full-book history request or execution DOM work. Updates are coalesced, and chart drawing uses the existing visible/dirty scheduler. Server admission uses bounded 5000-record / 8 MiB database pages, at most four simultaneous HTTP responses, a 512 MiB container memory limit and 0.5 CPU quota.

Bounds: 61 retained finalized seconds; up to six pending seconds under the maximum lateness allowance; 2048 sparse price levels per second; 131072 recent execution IDs plus a bounded eviction queue; 7200 engine pane observations (1800 in UI batches); 2882 calibration references; 2048 events. Rolling quantities and extrema update incrementally. Exact six-part and execution-duration evidence uses per-second side/price quantities and first/last actual execution timestamps. Capacity loss invalidates affected analysis instead of issuing a falsely complete signal.

The reproducible diagnostic command is `node scripts/effort-result-bench.mjs`; `EFFORT_BENCH_RATE` selects synthetic event-time rate. The recorded host reported Linux ARM64, four Cortex-A76 logical CPUs and 7.77 GiB RAM, with other desktop/browser work present. One million executions over 1000 event-time seconds at 1000/s, 11 prices and 1000-record batches took **4733 ms**, about **211289 executions/s** computational throughput; maximum batch **37.2 ms**, observed heap delta **32.4 MiB** (not peak/retained memory). It evaluated 969 gated zones, retained six events, 61 seconds and 60002 IDs, with zero capacity warnings. A separate million-record 10000/s / 100-second saturation run took **2844 ms**, max batch **46.7 ms**, and produced seven explicit identity-capacity warnings and no signals. These are synthetic engine checks on the reported host, not live-feed acceptance, chart frame-rate certification, device-wide Raspberry Pi qualification or trading-edge evidence. JSON measurements are in `artifacts/effort-result/`.

Focused fixtures cover specification acceptance cases, exact percentile/coverage boundaries, calibration cutoff, late/corrected data, gaps/epochs, frozen zones and settings, three-close timing, overlap/cooldown, unsuccessful retention, scaling, zero/null, reload notification suppression, shared ownership and replay prefixes. Browser checks cover catalogue/settings, signed pane, evidence, themes, visibility and removal. See the repository test commands and the checked-in tests for reproducible details.

## Deferred optional work

Release 1 ships 30 seconds only. The optional 10/60-second horizons need independent six-part timestamp partitioning and calibration. Synchronized midpoint history, receipt-time modes, depth/OFI evidence, iceberg inference, existing-level context attachment, seasonal references, expected-impact regression/ML, cross-venue scores, automatic execution and generic alerts/journaling/backtesting products are not included. No nonfunctional switches for them are exposed. The source contract, deterministic engine, event records and renderer boundary remain available for bounded future extensions.

## Server operation and verification

The Compose `effort-result` service starts independently of chart subscriptions and restarts under `unless-stopped`. It reads the existing USD-M collector on port 18784 and ClickHouse with existing application credentials, and serves a private loopback API on 18786 through the existing 18780 gateway. `/v1/effort-result/health` reports source state, progress, configuration count and resource metrics. It requires no ClickHouse schema migration. The existing candle, depth, spot and Level Watch collectors are unchanged.

`ops/sync-effort-engine.mjs` in the server repository copies the canonical client/replay engine and settings with only import-path adaptation; `--check` verifies no drift against the sibling client checkout. Server and client use the same formulas and event reducer. Server tests cover real-input calibration restoration without historical events, continued observation without HTTP consumers, restart eligibility, bounded configuration registration, source rejection and persistent notification claims. Client tests cover shared polling, stale/unavailable server states, historical-alert suppression and per-consumer controls. Live verification is recorded separately from synthetic fixtures.
