# Hyperliquid BTC Trading R1

This panel adds manual BTC perpetual account monitoring and order controls to the existing terminal. The application still has no backend account service. Public reads and signed actions go directly from the browser to Hyperliquid using the pinned `@nktkas/hyperliquid` SDK. The scope is Hyperliquid BTC perpetual only; it does not add automated strategies, other assets, Binance execution, or custody.

## Account and agent setup

The panel needs two addresses:

- **Principal / sub-account**: the address whose balance, positions, orders and fills are queried, and whose trading permission is targeted.
- **Agent**: a separate API-wallet address whose private key signs trading actions after that agent has been authorized for the principal.

Hyperliquid API wallets are signing keys. Queries must use the actual master or sub-account address, not the agent address. This panel keeps those identities separate and checks the selected network and principal before signing. See [Hyperliquid API wallets](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/nonces-and-api-wallets) and the [Info endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint).

Suggested onboarding:

1. Open **Trading · HL BTC** from the footer and select **Testnet**.
2. Sign in to the official [Hyperliquid testnet interface](https://app.hyperliquid-testnet.xyz/) or use the testnet steps in the [official faucet guide](https://hyperliquid.gitbook.io/hyperliquid-docs/onboarding/testnet-faucet). The panel does not implement email / Privy login or wallet connection; copy the principal account address shown by the official interface into **Principal account**.
3. Click **Connect**. Account reads use that principal address and the selected network. A testnet account and its authorization are separate from mainnet.
4. Create a dedicated API wallet in this panel with **Generate agent**, or use **Import agent** for an existing dedicated API-wallet private key. The application can generate an agent key, but never generates or asks for the principal's master seed phrase or private key. Do not paste a master-wallet or email-wallet secret into **Import agent**.
5. Copy the displayed **Agent** address. In the official Hyperliquid interface, authorize this API wallet for the intended master account or sub-account. Review the exact address and any expiry there, and approve it with the official account flow. This panel cannot authorize or revoke an agent on your behalf. Hyperliquid documents the API-wallet approval action in the [Exchange endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint).
6. Use a strong vault passphrase and click **Unlock**. The browser verifies the agent against Hyperliquid's current API-wallet list for the selected principal before enabling mutations.

Email sign-in and Privy are handled only by Hyperliquid's official interface. This application does not receive an email address, one-time code, Privy credential or wallet-provider session.

## Vault, lock, remove and revoke

The dedicated agent private key is encrypted before it is written to this browser's IndexedDB. New records use version 2, a random 16-byte salt, scrypt (`N=32768`, `r=8`, `p=3`) and AES-GCM with a random 12-byte IV. The storage key and authenticated additional data bind the record to the selected network, normalized principal, agent address, version and exact KDF profile. The raw derived key bytes and temporary key buffers are cleared after use. The passphrase must be at least 12 characters; choose a longer, unique passphrase that you do not reuse elsewhere.

Version 1 records are unscoped legacy data encrypted with the bounded scrypt profile `N=32768`, `r=8`, `p=1`. They are never treated as the selected principal's remembered agent. After passphrase decryption, the worker verifies the derived agent address and its current non-expired authorization. The panel then asks for a separate confirmation naming the testnet/mainnet network, principal and verified agent. Confirmation prepares a version 2 ciphertext and moves it in one IndexedDB transaction that compares the exact legacy source, requires the destination to be empty, adds the scoped record and deletes the legacy record. Wrong passphrases, failed authorization, a declined confirmation, a conflicting destination or a canceled transaction leave the legacy record unchanged. Lock or account changes invalidate pending binding work.

The browser stores the ciphertext, salt, IV and public agent address in IndexedDB. The selected network and principal, plus the bounded order-attempt journal, are stored in localStorage. Private keys and passphrases are not written to localStorage, the dock layout, a server or a trading journal. Unlock loads the key into the dedicated worker and signer memory for this browser tab. **Lock** drops the worker's signer references and releases its same-origin Web Lock. The default inactivity timeout is 15 minutes; choose a whole number from 1 to 120 minutes in the panel. Existing saved settings without a timeout keep the 15-minute default. The worker checks for inactivity every 10 seconds. Closing the app terminates the worker. Browsers without the Web Locks API remain read-only.

Persistent vault use requires IndexedDB, Web Crypto, secure randomness and a secure browser context. If IndexedDB is unavailable but those signing capabilities are present, the panel offers a **session-only agent**. That key stays only in the current worker/tab and is erased by Lock, the timeout, reload or close; it is never passed to the persistent vault writer. If Web Crypto, secure randomness or the secure-context signal is unavailable, signing and key generation stay disabled. Network/account settings and the bounded attempt journal may be session-only if localStorage is unavailable.

The Web Lock coordinates tabs in the same browser profile and origin. It does not coordinate other devices, other browser profiles or actions made in the official interface. There is no cross-device nonce lock.

The lifecycle actions have different effects:

| Action | Effect |
| --- | --- |
| **Unlock** | Decrypts the saved agent key into the worker and checks current authorization for this principal/network. |
| **Lock** | Clears the active signer and releases local tab ownership. A session-only key is discarded; a persistent encrypted record and Hyperliquid authorization remain intact. |
| **Disconnect** | Stops public account reads and locks the signer. It retains the remembered network/principal, attempt journal and encrypted agent record. A session-only key is discarded. |
| **Remove encrypted key** | Deletes this browser's encrypted IndexedDB record. It does not lock another device, revoke the agent at Hyperliquid, cancel orders or close positions. |
| **Forget this device** | Removes the encrypted key when present, remembered account/network, local attempt journal and any session-only signer. It does not cancel exchange orders, close positions or revoke Hyperliquid authorization. |
| **Revoke / deregister** | Do this in the official Hyperliquid account interface. It removes Hyperliquid authorization; the local ciphertext remains until separately removed. |

If an agent is revoked or compromised, stop using it, revoke it through the official account interface, and remove the local encrypted record. Create a fresh agent for future use; Hyperliquid notes that deregistration can prune an agent's nonce state, so the address should not be reused. Removing the local record alone is not revocation.

## Trading behavior and limits

- This release accepts only the native `BTC` perpetual contract. It does not convert or route other instruments.
- GTC and IOC limit orders use exact decimal input and BTC size precision from live Hyperliquid metadata. Invalid size/price precision is rejected before signing.
- The market option sends a **protected IOC limit** around the latest midpoint, with outward rounding and a user-visible slippage bound. It is not a market-order guarantee: it may fill partly or not at all, and IOC cancels any unfilled remainder.
- Position rows include **Close 25%**, **Close 50%** and **Close 100%** actions. Each calculates the requested fraction from the current BTC position, rounds down to live `szDecimals`, enforces Hyperliquid's $10 minimum notional, and submits one opposite-side reduce-only protected IOC after a confirmation showing network, account, percentage, size and slippage bound. If the IOC only partially fills, the next account snapshot determines the remaining position and existing protective orders stay in place. If a fresh snapshot confirms the position is flat while reduce-only TP/SL orders remain, the app offers a second confirmation to cancel only those BTC trigger orders; it never cancels them automatically or during a partial close.
- A take-profit or stop-loss request is a reduce-only trigger order. Its trigger is a limit trigger, using the displayed limit and trigger prices. The application sends TP and SL as separate actions; they are not an atomic bracket with the entry, and the app cannot guarantee that both will remain appropriate as the position changes.
- Leverage changes are sent for BTC only. Exchange risk limits may reject otherwise valid values.
- Modify and cancel controls operate on currently visible BTC open orders only. A partial fill, fill, trigger or cancel that races with the request can change the outcome. The next live snapshot is authoritative.
- Each submission uses one client order ID and records its intent and status. A transport timeout or ambiguous response is shown as unknown and reconciled using that ID. The client does not automatically repeat an uncertain order, modify or cancel request. Check the exchange and refresh before choosing any manual retry.
- Partial executions are tracked by client order ID and exchange order ID. The UI shows cumulative filled size and open remainder; a resting GTC order stays partially filled until an authoritative full-order status arrives. An unknown order lookup never upgrades an attempt to filled. For IOC orders, a partial fill is terminal: no remainder is shown as resting, the canceled quantity is stated in the attempt status, and the fill total remains the executed amount.
- Current agent authorization is queried immediately before each signed mutation. An absent, expired or revoked agent remains read-only.
- Chart trade levels are presentation of the current public account snapshot and mark/mid prices. They are available only when the trading panel is set to mainnet because the displayed Hyperliquid candle feed uses mainnet prices. On testnet, the chart overlay and chart-context order drafts stay disabled with that reason shown; the separate trading panel continues to support testnet reads and actions. A chart candle price is never used to draft a testnet order. Dragging a mainnet level creates a draft and requires explicit confirmation before an order modification is sent; Escape or a failed save restores the authoritative level. These levels are not chart drawing objects.

The order formats follow Hyperliquid's [Exchange endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint). SDK request completion is not a guarantee of execution or final order state.

## Mainnet safeguards

Mainnet starts only after selecting it and connecting a principal address. Every mainnet signing action uses a confirmation dialog; the user must type the exact word `MAINNET` before the confirmation button enables. This applies to order placement, order modification/cancellation and leverage changes. Legacy-key binding is a local vault migration and separately names the selected scope; removing or forgetting an encrypted record is local-only. The typed guard is an interaction check, not a protocol restriction: an authorized agent key can still act outside this application. Verify the principal, network, side, size, price, reduce-only flag, order type, trigger and slippage bound before confirming. No mainnet signed call or order was used for the R1 acceptance evidence below.

Use Testnet with a dedicated agent and no mainnet key. For a bounded hands-on check:

1. Compare the selected principal's account value, positions, open orders, fills, BTC mark and mid against the official testnet interface; begin flat with no open orders.
2. Import or generate a dedicated agent, authorize that exact address on testnet and unlock it. Check that new ciphertext is version 2 and scoped to the selected testnet principal. For a legacy record, verify the separate confirmation names the exact network, principal and agent; declining it must leave the legacy record available and locked.
3. Lock and reload. Confirm the principal and encrypted-agent indicator return while signing stays locked, then unlock with the vault passphrase and compare the account again.
4. If order acceptance is needed, use one unique-cloid, far-resting GTC capped at `$13.50`, reload while it remains open and locked, unlock and cancel only that order in the terminal. Recheck positions and both open-order views through the testnet Info API.
5. Keep mainnet confirmation as a UI-only check: inspect the exact action summary and verify submission stays disabled until `MAINNET` is typed. Do not send a mainnet order.

The evidence below separates deterministic unit/browser checks from direct-adapter and native-app testnet checks. Neither mocked exchange responses nor accepted-but-untriggered TP/SL orders establish trigger execution or production readiness.

Read-only testnet transport probe (2026-10-31): run `pnpm probe:hyperliquid-reconnect` to repeat the check. Using the public zero-address principal, REST returned account value `62.804826`, no positions and no open orders at probe time. The `clearinghouseState` and `openOrders` WebSocket subscriptions each delivered an actual initial snapshot. After forcing a reconnect through the SDK reconnecting socket, both subscriptions delivered again, and a fresh REST read returned the same account value, position count and open-order count. The script instantiates no `ExchangeClient` and calls no signed endpoint. It verifies public zero-address stream recovery only; it does not verify a populated account, signed actions or testnet order execution.

## Security review and operational caveats

The API wallet is still a signing secret. While unlocked, a malicious script executing in this origin, a compromised dependency, a browser extension with page access, or access to the browser profile could capture inputs or invoke the worker. AES-GCM protects the stored record against offline reading without the passphrase; it does not protect an unlocked browser from same-origin code execution. This release uses a passphrase-derived vault key; it does not include WebAuthn/PRF, biometric or hardware-key vault unlocking. The worker and Web Lock reduce accidental exposure and duplicate signing, but they are not a hardware security boundary and JavaScript strings cannot be reliably zeroized.

This repository has no HTTP response-header configuration for Content Security Policy. `index.html` also contains an inline style block. A deployment must set and verify CSP, `frame-ancestors`, transport security and origin policy at its hosting layer, allowing only the required same-origin assets and the official Hyperliquid HTTP/WebSocket endpoints. Do not claim CSP protection until the deployed response headers have been inspected. Review and update the exact pinned Hyperliquid SDK, viem, noble hashes and decimal.js dependencies with their lockfile and license notices.

## Architecture

The panel and settings stay in native DOM. `TradingController` coordinates a dedicated module worker. The worker consumes the venue-neutral `TradingVenueAdapter` domain contract; `HyperliquidTradingAdapter` is the concrete boundary that owns SDK clients, WebSocket subscriptions, Hyperliquid normalization and exchange payload mapping. The worker owns bounded normalized account state and the active per-tab signer, and checks current principal authorization before each signed mutation. A fresh workspace does not instantiate the trading worker; a remembered principal reconnects public data during startup. The signing owner uses Web Locks plus BroadcastChannel status messages. The chart overlay is a public OpenAlgo primitive and keeps chart gestures separate from native drawing tools.

The selected BTC series remains independent of existing candle, Footprint and OpenScript feeds. This release adds no server endpoint, backend secret, chart engine, React UI, automated strategy or non-BTC venue connection. Direct public-account availability remains subject to Hyperliquid endpoint reachability and websocket reconnects; stale/error state stays visible, and public reads do not switch to fixtures.

When explicit diagnostic fixture mode is selected, public account reads remain read-only. The controller and trading worker both reject agent creation/import/unlock and every signed exchange action. The worker selects the mode once and rejects any later attempt to change it while that worker is alive. Test-only browser workers are injected by the Playwright harness in non-fixture mode; the production app has no test override for enabling orders during fixture mode.

Run `pnpm test:trading:browser` to build with diagnostics enabled and run the complete Trading browser spec. Append `--grep 'test name'` to run a focused case. This check requires `VITE_DIAGNOSTICS=1` because it reads the native `window.__terminal` diagnostics hook; the ordinary `pnpm build` keeps diagnostics disabled.
