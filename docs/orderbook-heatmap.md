# Streaming order-book heatmap

Enable **Heatmap** beside Indicators on either Candles or Footprint; the gear opens its settings. Initially only **Binance BTCUSDT USD-M Perp** is supported. Spot and Hyperliquid remain usable ordinary charts and explicitly report the unavailable layer. This is resting BTC liquidity, not executed footprint volume. Depth changes alone cannot distinguish cancellation from execution.

Collection starts on enable, uses browser-session memory, and clears on reload or removal of the last consumer of that resolution. Interval switches retain collection; settings and enabled state persist with the layout. In Footprint mode, the chart toolbar's Price level controls both layers. The heatmap uses the same fixed lower-bound price grid and row height as executed footprint cells; its separate row control is read-only. Candle mode retains its independent heatmap row setting. Switching modes can change the effective collection resolution and therefore start fresh collection unless another consumer already retains that grid. Changes to row width or 250/500 ms bucket size start a new configuration unless another consumer already retains that exact configuration. Visual changes preserve collection and viewport. Earlier candles have no implied book history.

## Data and coverage

The feed worker shares the existing synchronized Binance diff-depth book with OpenScript depth studies. There is one `/public/ws/btcusdt@depth@100ms` socket and one 1,000-level snapshot per synchronization attempt, independent of the number of studies or heatmaps. Consumers are reference counted independently. Tick size is obtained from validated Binance exchange metadata; no guessed tick fallback is used. Absolute quantities replace levels and zero deletes them. Snapshot bridging uses `U <= lastUpdateId <= u`; subsequent diffs require `pu` equal to the preceding `u`. Sequence gaps, reconnects and more than five seconds of silence invalidate collection until synchronization succeeds. See [Binance's official synchronization rules](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-market-streams/How-to-manage-a-local-order-book-correctly).

Rows use integer tick-grid grouping, with bounds `[low, high)`. Both chart types use fixed lower-bound grids. A $25 bucket starting at $82,800 covers [$82,800.00, $82,825.00); a level exactly at $82,825 enters the next bucket. Footprint executions use the same integer-tick grouping. The chart adapter converts lower bounds to OpenAlgo cell centres only for rendering. Boundary trades and book levels enter the same row; the two quantities remain distinct resting versus executed measures. Simultaneous price levels are summed in BTC, separately for bids and asks. Piecewise-constant book state is integrated over **host-observed UTC receipt milliseconds**, including irregular update spacing. A repeatedly observed 20 BTC wall remains 20 BTC. Average quantity is integrated BTC-milliseconds divided by observed duration; peak is the maximum simultaneous quantity observed through this supplied stream, not a guaranteed intraupdate maximum. Same-millisecond observations still contribute peaks. Buffered snapshot states are not projected backward before collection starts.

The original outer snapshot prices remain conservative coverage boundaries for each synchronization epoch. Interior empty rows are known zero; outside prices are unknown. Edge rows, clipped coarse rows and capacity-limited data are incomplete subtotals and are marked as such. Outages create separate raw epochs with no observations during the gap. Entire unobserved candle intervals have no column; interrupted intervals have incomplete columns. Missing durations never contribute zero quantity or stale walls to an average. A delayed worker timer extrapolates at most five seconds, then leaves a gap.

## Rendering and interpretation

The repo-owned Canvas2D `OrderBookHeatmap` uses OpenAlgo Charts 2.6.0's public primitive interface: bottom z-order, null autoscale contribution, host update requests, rendering context and non-draggable hit testing. It stays behind candles and footprint cells. The library and dependency licence set are unchanged; no upstream files are patched.

Each actual host candle has exactly one heatmap column, anchored to its logical slot (`index - 0.5` through `index + 0.5`); in Footprint mode its painted edges match the ladder width and candle gutter. The first observation paints the full forming-candle column; subsequent observations update its quantity without moving its edges. This is a display slot, not a projection of the book into the future: hover retains the actual observed time span and labels partial intervals. A missing host interval has no slot and is not painted into an unrelated bar. No synthetic time-axis bars are inserted. Interval switches regroup retained raw observations into the new candle columns. Time-scale spacing, manual price scaling and the existing visible-panel scheduler are retained.

LOD uses screen-space geometry: readable cells show quantity-only labels fitted to their height and width (9–24px, with padding); smaller cells omit text; distant Candle views omit labels and combine power-of-two price rows into horizontal bands while retaining candle-aligned column boundaries. Footprint views align heatmap width to the ladder, reserving the slim candle gutter, and keep the exact footprint price rows at every zoom level, omitting labels when space is insufficient. The worker's 250/500 ms observations are duration-weighted within each candle, rather than displayed as individual columns. Quantities are aggregated before colour lookup. Time averages divide by retained observed duration, excluding gaps; price quantities sum simultaneous rows. Multiple synchronization epochs within one candle share its column but mark it incomplete. Retention can leave only part of an older interval; hover labels that partial interval instead of implying complete candle history. Worker-maintained coarse peaks preserve simultaneous sums rather than adding unrelated per-row maxima. A visible one-sided row fills its entire height. When both bid and ask quantities pass the minimum filter in one row, they occupy separate upper/lower halves; hover uses the same visible-side rule. Hover gives actual time and price bounds, side, BTC quantity, average/peak mode and incomplete coverage.

A fixed ordered purple/blue/teal/green/yellow palette uses logarithmic **BTC per $10 price width**, so a wider price bin does not automatically look like a stronger wall. Hover reports the actual aggregated BTC quantity, not this normalized density. Defaults are $10 rows, 500 ms buckets, average mode, 45% opacity, fixed intensity 100 BTC/$10, minimum 0.01 BTC and Auto labels. Scaling never adapts merely because the viewport changes. A bounded price-projection cache reuses unchanged tile revisions during pan/time zoom (one factor per retained tile, at most 240 entries and 16,384 projected rows); cached geometry rebuilds when data or viewport changes; hidden panels retain data without painting. Captured depth does not expand price autoscale.

## Limits and transport

Each of at most four active resolutions retains at most 240 buckets, 128 captured rows per bucket, 16,384 cells and 2 MiB of accounted typed payload plus bucket metadata. At 500 ms, 120 seconds is an upper bound; dense configurations evict sooner. Row capture is centered within the snapshot boundaries; clipping is explicitly capacity-limited. These are cache bounds, not hard total browser-process heap bounds. Shared pending snapshots and each chart's bounded index/cache also consume memory; geometry and canvas allocations remain browser owned.

The source book is additionally limited to 10,000 levels per side, with at most 512 buffered diff events and 20,000 buffered level updates; exceeding limits forces resynchronization. Publication is 2 Hz, independent of rendering FPS. Each resolution allows one unacknowledged envelope, coalescing replacement revisions into a bounded pending map. A joining consumer receives current retained state; stale generations and acknowledgements are rejected. Removing the final resolution stops the timer and book observer; an independent depth study can keep the source alive. Diagnostic counters expose configurations, consumers, publications, CPU time, retained cells/bytes, evictions, pending batches, geometry rebuilds and render p95.

The canonical v1 tile is independent of OpenAlgo: UTC start/end, epoch, row width, lower-bound grid offset (zero for current fixed buckets), revision, incomplete flag, packed Float64 rows (price low; bid/ask BTC-ms; bid/ask observed peaks; bid/ask observed and complete durations), plus bounded power-of-two simultaneous peaks. Future durable storage needs explicit instrument/session identities, versioned serialization and a recording service; this milestone creates none.

## Reproduction

```sh
pnpm typecheck
pnpm test
VITE_DIAGNOSTICS=1 pnpm build
pnpm preview --port 4173
pnpm test:browser
node scripts/bench-heatmap-collector.mjs
TERMINAL_URL=http://127.0.0.1:4173 node scripts/bench-heatmap-browser.mjs
```

Browser depth fixtures are confined to explicit test transport and diagnostic checks. Normal builds never substitute synthetic liquidity. For the genuine public-feed check, build without `VITE_DIAGNOSTICS`, serve it separately and run `TERMINAL_URL=<ordinary-preview> node scripts/live-heatmap.mjs`. See [verification results](verification.md#order-book-heatmap) for measured Pi performance, browser limitations and live evidence.
